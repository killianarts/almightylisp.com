9.5ERRORS & CONDITIONS

Preserving Your Stack

Being able to signal a condition, and then choose how to respond based on the condition is very nice, but Lisp has one more trick up its sleeve.

handler-case has a problem: it unwinds the stack. That means that you lose local state at the point where you decide to do something with a naughty-word condition. In this case, the debugger never popped up. Instead of manually choosing the restart for the broken lines, we used invoke-restart to skip them for us.

What if we try to call invoke-restart inside the handler-case version?

Won't work. The stack has been unwound, so we no longer have access to the skip-line restart. And you need restarts to be able to return to the loop iteration. If you call a normal function inside the handler-bind, the condition won't actually be handled. Instead, it will be "propagated" to the next outer call to handler-bind that also handles the same condition. invoke-restart is how you stop the propagation of the condition, handle the condition, and restart the process at the point where the condition was signaled.

9.6ERRORS & CONDITIONS

Safely Unwinding

You often want a way to run "clean up" after a process completes, erroneously or not. For example, if you successfully write to a file or database, you want your stream or connection to the file or database closed. And of course, if you do encounter an error, you don't want to leave your data in a malformed state.

unwind-protect is how you run clean up actions like closing connections. We'll use it later in the Account Library chapter to close database connections for us.

In the example above, the body will hold whatever forms you want to run with an open DB connection. The first argument to unwind-protect is the form you want to run. The second argument is your cleanup operation that you always want to run after the previous form returns.

Typically, you don't write unwind-protect directly; as explained in the section on Streams in the LISP FUNDAMENTALS chapter, with-open-file uses unwind-protect internally to close the open file connection once your operation is complete. Many macros using the with-* naming convention use unwind-protect internally.

9.7ERRORS & CONDITIONS

Ignoring Errors

There are times when you don't want errors to open a debugger, you just want to have information about the kind of error.

ignore-errors is used for doing just that.

If a form in ignore-errors returns an error, ignore-errors itself will return two values: NIL and the condition object with the error. Otherwise, it simply returns the return value of the last form in ignore-errors.

9.8ERRORS & CONDITIONS

Built-in Conditions

There are a number of built-in conditions that you can signal in your own code. Examples include style-warning, type-error, arithmetic-error, etc. You can find a complete list in the Hyperspec (https://cl-community-spec.github.io/pages/Condition-Types.html).

9.9ERRORS & CONDITIONS

Built-in Restarts

In addition to being able to invoke your own custom restarts, you can invoke any of the built-in restarts:

  • continue
  • store-value
  • use-value
  • muffle-warning
  • abort

While playing around with code in this book you've probably seen most of these restarts already. muffle-warning is useful for times when you have some warn call that is filling your REPL with noise that you want to suppress.

For these built-in restarts, there are also corresponding functions (https://cl-community-spec.github.io/pages/f_abort.html) that you can call.

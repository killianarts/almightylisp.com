#+TITLE: The magazine

The Shiso module behind the site's root, =/=: articles written as org files in
=content/magazine/=, served live, and published as static pages to
=static/magazine/published/=. The design is Figma's /Neoindustrial/ file:
the frames /Homepage restyled · C1 · Landing/ and /Article restyled · C1 ·
Landing/, which are the v30 cards and article sections on a light page,
with black kept for the book, the featured series, section heads and the
footer.

Writers need only =content/magazine/WRITING.org=. This file is for
changing the code.

* How a page is made

1. A request reaches a controller (=controllers.lisp=), routed by
   =routes.lisp=: =/=, =/archive=, =/article/:slug=, and
   =/search=, which answers the search palette (see [[*Search and the archive's filters][Search and
   the archive's filters]]).
2. The controller asks the model for the articles and series. The model
   (=model.lisp=) keeps them in an =almighty-press= collection, which reads
   =content/magazine/= and its series' folders again whenever a file there
   changes.
3. If they did change, the controller first writes every page to
   =static/magazine/published/= (=publish.lisp=).
4. A =page-= function (=hypermedia/=) renders the page with almighty-html,
   and the controller sends it with =Cache-Control: private, max-age=60=,
   which htmx's preload extension needs (see [[*Navigation and effects][Navigation and effects]]).

Parsing org, watching files, dates, inline markup and writing pages are in
=lib/almighty-press/=, which knows nothing about the magazine and can be
used for another site.

* The model

=model.lisp= turns org into three structs:

- =article= :: one file in =content/magazine/= or a series' folder. Its
  =sections= are almighty-press sections whose blocks are press's, except
  that =#+BEGIN_NOTE= becomes =(:note label paragraphs)= and a source block
  gets =:highlight=, its highlighted line numbers. Source blocks that share
  an =:evolve= name are steps of one piece of code: =mark-steps= adds the
  lines a step added to its =:highlight=, and gives it =:moved=, the lines
  it changed. Its =code= (serial) is
  made from the topic, type and date unless =#+CODE= is given. Its =series=
  is the code of the folder it's in.
- =series= :: a folder in =content/magazine/= (except those in
  =*not-series*=, i.e. =templates/=): its =series.org= holds the keywords,
  and its other files are the parts.
- =part= :: a series' part: a number, a title, and its article, or NIL
  while the part is a draft. =read-series= builds them from the folder, so
  a part's title and number come only from its own file.

An article with =#+LAYOUT: evolving= has =layout= =:evolving=. Its sections
are the same blocks; =section-evolution= reads a section as what the page
needs: the notes and source blocks that can stand beside the text, and the
paragraphs, each with what is beside it. Its docstring has the rules.
=hypermedia/evolving.lisp= writes that out as plain markup, and
=static/js/magazine-evolving.js= builds the moving page from it; the
styles are under /Evolving articles/ in =magazine.css=.

=load-magazine= reads it all: the standalone articles, then each series'
folder. Drafts are read, so a queued part has a title, but only published
articles are returned.

Checks that stop the magazine loading: missing =TITLE=; missing =DATE=,
=TYPE= or =TOPIC= outside a draft; a type or topic that isn't in
=*article-types*= or =*article-topics*=; text before the first heading;
=#+SERIES=, which the folder replaced; =#+PART= outside a series' folder,
or missing inside one; a series with a missing or repeated part number; a
folder with no =series.org=; a =series.org= that lists parts; two series
with one code; two articles with one slug; a =:highlight= that isn't line
numbers within its source block; an =:evolve= with no name; a =#+LAYOUT=
other than =evolving=; and,
in an evolving article, a note or source block with no paragraph to belong
to, or a paragraph followed by the wrong number of source blocks. An
unknown keyword only warns.

=homepage-layout= decides what the homepage shows (its docstring lists
the plist it returns), and =keep-reading-articles= what follows an article
outside a series.

To add a topic or type, add it to =*article-topics*= or =*article-types*=
with its two-letter code, then describe it in =WRITING.org= and, for a
type, add a template in =content/magazine/templates/=.

* The pages

Every page is an =ac-sheet-page= (=sheet.lisp=): the grey sheet with the
running header, nameplate and date strip, then the page's bands, then the
running footer. A band is an =ac-band=:

#+BEGIN_SRC lisp
(ac-band :class "latest-band"
         :side (list "Latest  ■  4 articles" "Archive")   ; gutter labels
         :marks t                                         ; gutter marks
  ...content in the main column...)
#+END_SRC

=:marks= draws the band's gutter marks: a dot pair at the top of each
gutter and a gauge at the foot of the right one (=:foot= for the gauge
alone). The two kinds of dot pair change sides from one marked band to the
next, counted in =*marked-bands*=, which each page function binds around
its render. Only =ac-band= counts, because a component's body runs as the
page is rendered, in page order; a plain function called in a template
runs earlier.

Bands are placed on fixed rows of the sheet's grid by their class, in
=magazine.css= under /The sheet/. A new kind of band needs a row there.
Sections that start with a big black heading use =render-section-head=,
whose =key= names the two bands it makes (=KEY-gap=, =KEY-head=).

Components reused across pages:

| Function                 | Where                                                   |
|--------------------------+---------------------------------------------------------|
| =render-article-brief=   | Latest, Keep reading, not found                         |
| =render-book-brief=      | Keep reading, when an article names a book chapter      |
| =render-book-band=       | The book's band on the homepage, under the plate        |
| =render-book-ad=         | The compact book panel beside an article                |
| =render-book-panel=      | What that panel and the footer's book hold              |
| =render-gauge=, =render-dot-pair= | The ornaments: gutters, section heads, black panels |
| =render-eyebrow=, =render-progress-bar= | Over and under a heading: sections, briefs in a series |
| =render-index=, =render-index-cell= | The end of a series                           |
| =render-series-progress= | Series cards, the end of a series                       |
| =render-headline=        | The lead and an article's lede, scaled to fit           |
| =render-lede-row=        | The dek and byline under either headline                |
| =render-end-band=        | Under an article's end head; not found                  |
| =render-hatch=           | Leftover space at the bottom of a column                |

Text from org goes through =render-inlines= (=package.lisp=), which links a
bare =[[slug]]= to that article. Magazine links come from =s:url=; the
book's link is written out in =*book-href*=, because Shiso only knows where
another module is mounted after that module has served a request.

=joined= puts the =■= between facts in labels, so every label is spaced
the same; =slashed= does the same with a slash, for eyebrows.

An article's section (=render-piece=) is one cell: its heading, then its
blocks in the order they are written, notes included. Paragraphs, lists
and notes keep to a measure at the left; the heading, code blocks and
tables run the cell's width.

** Series logos

Each series code has a logo in =*series-logos*= (=logos.lisp=): a fill
rule and one SVG path on a 48-unit grid, built from =path-rect=,
=path-poly= and =path-bar=. The logo is filled with =currentColor=, so CSS
sets its colour. A code without an entry gets a square.

* The stylesheet

=static/css/magazine.css= has five parts, in order:

1. *Tokens*, on =.mag=: colours (the black panels are =--ink=; the
   =--night-= steps are the greys on them), the hatch pattern, fonts,
   cell padding (=--pad=), and the column ratios (=--cols-lead=, =--cols-index=). The narrow layout mostly
   works by changing =--pad=.
2. *Base*: element defaults inside =.mag=.
3. *Roles*: type and layout many components share. /Display/ (Science
   Gothic in capitals), /captions/ and /labels/ (Construct Mono, tracked),
   /summaries/ (Mohave), /tiles/ (cells divided by 1px white rules),
   the /lead split/ (two thirds and one third), /cells/ (padded panels on
   the sheet), and columns that end in a hatch. A component class is
   added to a role's selector list, then its own rule sets only what
   differs.
4. *Components*, in page order: the sheet and its rows, furniture, header,
   nameplate, strip, patterns, ornaments (gauges, dot pairs, eyebrows and
   progress rules), specs, buttons, section heads, series marks, the lead,
   the featured banner, the book panel and the book band, the footer,
   briefs, series cards, Latest, the article, contents, sections, code,
   tables, the end band, indexes, and the contents strip.
5. *Responsive* (1180px drops the gutters, 980px stacks the columns),
   then the screen effects and view transitions.

The =body::before= and =body::after= rules at the top are the site-wide
film grain and scanlines.

* Navigation and effects

The body is =hx-boost:inherited=: htmx (version 4) boosts every link
below it, so links within the magazine swap the body's contents instead of
loading a page, and its preload extension fetches a page when its link is
hovered. htmx 4 only hands an attribute down from an element that marks it
=:inherited=, so the book panel, the book band and the footer's shop cells
are =hx-boost:inherited="false"=, since their links leave the magazine.
=magazine-fx.js= sets htmx up: it keeps links that leave the magazine (the
other modules mounted in =src/main.lisp=, listed in =OTHER_SECTIONS=) from
being boosted at all, holds a swap until the screen effect has switched
the screen off, and loads a page the ordinary way when its request fails.

Back and forward fetch the page again and swap it in: htmx 4 keeps no
copy of the pages it leaves. Pages may be reused from the browser's cache
for a minute (=*page-cache*=), which keeps that quick.

htmx swaps only the body's contents, so the sheet carries the body's class
in =data-body-class=, and =magazine-fx.js= copies it to the body after
each swap.

=magazine-fx.js= also plays the hover flicker (on the book's buttons and
the book band's cards) and the tear when an article
or book link is clicked, then lets htmx (or the browser, for other sites)
navigate. With the search palette open over the page, the filter is on the
palette instead; in Safari the palette goes out of sight as the effect
starts. Safari (and every browser on iOS) runs the tear's SVG filter
on the CPU, far too slowly, so there the page is copied instead: three
copies tinted red, green and blue and added back together make the split,
and more copies in sliding bands make the tear (=buildSplit= and
=buildTear= in =magazine-fx.js=, =.fx-rgb= and =.fx-tear= in
=magazine.css=; see =ABERRATION-ANIMATION-DETAILS.org= for how both are
made and why). =magazine-toc.js= runs on article pages and is safe to run
again after a swap.

=dev/fx-lab/= is a test page for the effects: it plays them in a frame,
in the live version or another kept there (a whole copy of
=magazine-fx.js=, loaded for =?fx-lab=NAME=), and times them. It keeps the
ripple versions of Safari's split, set aside for costing about 10fps. It's
outside =static/=, so the site never serves it: run
=python3 dev/fx-lab/serve.py= (with the dev server up) and open
http://127.0.0.1:5090/fx-lab/.

=dev/fx-lab/overlays.html= (at =/fx-lab/overlays.html= there) is a test page
for the noise and the scanlines: it draws them on a page of the site one of
several ways, repainted as the site has them or painted once and moved, to
compare. Its comment says how to open it on a phone.

=magazine-fonts.js= runs first, in =<head>=. Once the page's stylesheets
and scripts are in, it loads the fonts itself and holds them back until they
have all arrived. If that takes longer than a
moment the page shows in fallback fonts meanwhile, and the switch happens
under the arrival effect (=MagazineFx.arrive= in =magazine-fx.js=). Add a
font to its =FONTS= list, and to =magazine-fonts.css=. The details are in
[[file:FONT-LOADING-DETAILS.org][FONT-LOADING-DETAILS.org]].

* Search and the archive's filters

Both are worked out and drawn on the server, and htmx sets the HTML into
the page. What a control asks for is in attributes written by
=hypermedia/search.lisp= and =hypermedia/archive.lisp=.

*Search.* Every page carries the palette, closed (=render-search-palette=).
=/=, Ctrl or Cmd+K, or the strip's first cell open it. That, and closing
it, is =static/js/magazine-search.js=: no request is needed for either.

What is being searched for is in the address a control asks:
=/search?q=window&field=body&sel=1&focus=4&wide=1= (=search-href=),
where =sel= is the article selected, =focus= the match in focus and =wide=
asks for more context. Typing asks for the query in the field that is
pressed, once it has paused for 150ms. Every other control (a field, an
article, a match) asks for the search as it stands with its own change
made, so the server decides what each one does next. The answer is the
palette's chips, list, preview and status (=render-search-results=), each
marked =hx-swap-oob="outerMorph"=: htmx changes the part of the page with
the same id to match, which keeps the panes where they were scrolled to. A
search asked for while another is on its way takes its place (=hx-sync=).

A control that a key stands for names the key in =data-keys= (=ArrowDown=
on the article after the selected one, =Enter= on the link that opens the
match), and =magazine-search.js= presses whichever control names the key.
So moving through results is a request each time, and the browser holds no
results. The link that opens a match is a link like any other, to the
match's section, so the page is fetched while the screen effect plays. It
also carries the matched text and which of its places in the section the
match is (=data-find=, =data-nth=); once the page is in,
=magazine-search.js= finds that place, scrolls to it and marks it
(=::highlight(search-match)= in =magazine.css=).

The text searched is each article's title, subtitle and body, as plain
paragraphs (=index-article=). It is made once and kept until the org files
change. A query is one phrase, matched whatever its case.

*The archive.* A type's or a series' row is a link:
=/archive?type=Tutorial&series=MAC=. The page it leads to lists
those articles alone, so a filtered archive can be linked to and works
without JavaScript. With htmx, pressing the row fetches that page, takes
the catalogue out of it (=hx-select=) and sets it in place of the one in
the page, and the row's address goes into the history, so Back undoes one
filter at a time. The server sends the same page either way. =?open==
opens a month (=2026-09=) or =all= of them. A month is a =<details>=, so
it opens and closes with no script.

To update htmx, copy =dist/htmx.min.js= and =dist/ext/hx-preload.min.js=
from the =htmx.org= package to =static/js/= and change the names in
=ac-magazine-document= (=hypermedia/sheet.lisp=). The package's
=dist/skills/= has an upgrade guide.

* Intel

Intel is a feed of short updates about Common Lisp projects: a release or
tag of a watched project, a new repository, or a post on a watched blog. Nothing is published
automatically. Updates are fetched into an inbox, and a person writes one
line for each update worth passing on.

| File                          | What it is                                                   |
|-------------------------------+--------------------------------------------------------------|
| =content/intel/watch.txt=     | The projects to watch: a repository URL a line, then a name  |
| =content/intel/blogs.txt=     | The blogs to watch: a feed's URL a line, then a name         |
| =content/intel/updates.sexp=  | The published updates, a plist a line. The site reads this; commit it |
| =content/intel/commits.sexp=  | Followed projects' commits this week: a count and the newest one's first line. Written by a fetch; commit it |
| =content/intel/inbox.sexp=    | Everything fetched and its status. Local; git ignores it     |
| =content/intel/following.sexp= | Followed projects' newest commits, and the last one seen. Local; git ignores it |

| Address                  | What's there                                                      |
|--------------------------+-------------------------------------------------------------------|
| =/=                      | The Intel band, under Briefs, once something is published         |
| =/intel=                 | Every published update by day; =?kind=release= or =?kind=new= keeps one kind |
| =/intel/desk=            | The desk: the queue, what's published, what's dismissed           |

*The desk* answers only where =:magazine/desk-enabled= is true: in
development by default; anywhere else with =INTEL_DESK=true=, or
=(setf (shiso:setting :magazine/desk-enabled) t)= in the REPL. Anywhere
else its addresses are not found, so the public site never serves it. Fetch now runs =curl= against each watched project's feed (GitHub,
GitLab, Codeberg or another Gitea or Forgejo host; any other URL is taken to
be a feed), against each blog's feed, and against GitHub's search for
repositories created in the last two weeks. =:magazine/github-token=
(=GITHUB_TOKEN=, a secret: set it in the environment or =.env=), when set,
is sent with the search only.
Publishing, changing a line and unpublishing write =updates.sexp= and the
static pages again; deploy them as you would an article.

*Following.* A project whose line in =watch.txt= starts with =*= is
followed; so is one whose card had Follow the project pressed, which writes
the =*= (and adds the line, for a repository the list didn't have). A
followed project's updates come first in the queue, marked Following. A
fetch also asks for its newest commits (on GitHub; other hosts have no feed
of them that is read here), and the desk's Following list shows those that
are new since Mark as seen was last pressed. The first fetch of a project
takes its newest commit as seen. Nobody writes a line for a commit; what
the site shows of them, in the band's Commits block, is each followed
project's count for the week and its newest commit's first line, which a
fetch writes to =commits.sexp=.

*Active elsewhere.* A fetch also asks GitHub which Common Lisp repositories
with twenty stars or more were pushed to in the last week, so an established
project nobody listed is still noticed. The desk's Active elsewhere list
shows those the watch list doesn't have: Follow the project adds one to
=watch.txt=, followed; Hide stops it being offered again. They are kept in
=content/intel/active.sexp=, local as the inbox is.

*Live.* =irc.lisp= is a listener on IRC: a thread that joins =#commonlisp=
on Libera Chat as =almighty-lisp-bot= and keeps the last 300 lines said
there, in memory only. It answers the server's pings and sends nothing else:
it never speaks. The desk's Live list has Connect and Disconnect, and shows
the lines as they arrive; while the listener runs, the homepage shows the
newest eight under the Intel band. Both lists ask =/intel/stream=
for themselves again every few seconds. Where =:magazine/irc-enabled= is
true (=INTEL_IRC=true=), the listener connects by itself on the homepage's first visit, which is
how the public site would show the channel; without it, nothing connects
until Connect is pressed. The server, channels and name are the variables at
the top of =irc.lisp=.

* Justified text

The site's body text is justified by =magazine-justify.js=: article
paragraphs (=.prose=), list items and margin notes, the lead's dek
(=.neo-dek=), the summaries on briefs and series cards, and the book
panel's pitch. The list is =SELECTOR= in the script, and the same elements
are named in the "Justified text" rule in =magazine.css=; add to both. It picks the line breaks for a paragraph as a whole,
so the spaces come out even, where the browser's own justifying fills one
line at a time. [[https://github.com/chenglou/pretext][Pretext]] measures the words on a canvas; the script then
wraps each line's text in a =.just-line= span that can't wrap, and the
browser stretches the lines (=.just= in =magazine.css=). Links, emphasis
and code are left as they are, and copied text has no line breaks in it.

It runs again when a column changes width, when the fonts switch in
(=magazine-fonts.js= calls =MagazineJustify.refresh=) and after an htmx
swap. The browser justifies a paragraph itself, hyphenating it
(=text-align: justify= and =hyphens: auto= in =magazine.css=), without
JavaScript, in a column under =MIN_SPACES= wide (phones: the script
doesn't hyphenate, so its narrow columns would be full of holes), or if
the paragraph holds anything but text in plain inline elements. Lists and
margin notes aren't justified; add them to =SELECTOR= and to that rule.

Pretext is written in TypeScript, but its npm package ships compiled
JavaScript. =pretext-0.0.9.min.js= is that, bundled into one file that
defines =window.Pretext=. To take a newer version:

#+begin_src sh
npm pack @chenglou/pretext && tar xzf chenglou-pretext-*.tgz
npx esbuild package/dist/layout.js --bundle --format=iife --global-name=Pretext \
    --minify --target=es2020 --outfile=static/js/pretext-VERSION.min.js
#+end_src

Keep the licence line at the top of the file, and change the name in
=hypermedia/sheet.lisp=.

* Publishing

The server publishes by itself: the first request after an org file
changes writes every page before answering. To force it from the REPL:

#+BEGIN_SRC lisp
(magazine:publish)
#+END_SRC

* Preview images

A link to an article shows a picture on X, Facebook, Discord and the like:
the article's preview image (Figma: Social Media · Article OG image). Its
page names it in its Open Graph tags; every other page names the site's
picture, =static/assets/images/x-posts-preview-image.png=.

Publishing draws each article's image that isn't drawn yet
(=og-image.lisp=): an SVG, made into a 1200 x 630 PNG in
=static/magazine/published/og/= by =rsvg-convert=. The file is named after
the slug and a hash of what it shows, so an image is drawn again only when
it changes, under a new name the social sites haven't kept. Images of
articles that changed or are gone are deleted.

The title is set as large as it fits, from 180px down to 54px: the largest
size whose lines fill the space above the subtitle, leaving a strip of
hatching. Its own line breaks (=\\= in =#+TITLE=) are kept. Past three
lines at 54px it is cut short with an ellipsis, and the subtitle past four
lines. SVG doesn't wrap text, so the lines are broken in Lisp, measured with
the font files' widths (=font-metrics.lisp=).

=rsvg-convert= must be installed where the server runs: =apt install
librsvg2-bin=, or =brew install librsvg=. Without it the pages still
publish, with the site's picture, and =/og-preview= says why. It draws with
the fonts in =og-fonts/= alone (=fonts.conf=), so an image comes out the same
on any machine: Science Gothic Medium and Mohave Regular, fixed from their
variable fonts with fontTools, Construct Mono, and JF Dot M+Q 10 cut down to
the running header's and footer's Japanese.

| Address                  | What's there                                                      |
|--------------------------+-------------------------------------------------------------------|
| =/og-preview=            | Every article's image at full size, and as X, Facebook and LinkedIn, Discord and Slack show it |
| =/og-preview?slug=SLUG=  | One article's                                                     |

=/og-preview= answers only where =:magazine/og-preview-enabled= is true: in
development, unless the setting says otherwise. It is for checking an image
on this machine before anyone sees it. The sites'
cards there are close copies of theirs; for a published page, the Facebook
Sharing Debugger and LinkedIn's Post Inspector show their own and fetch the
image again.

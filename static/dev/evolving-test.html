A window that won't stay

The waiting is usually called the event loop, or the run loop on the Mac.

Last time we got a window on screen. It opened, and by the time you could look at it, it had closed again. Nothing was wrong with the window. The program simply reached its last line.

A web page never has this problem, because the browser is already running and already waiting. A native application has to do its own waiting.

You can watch it happen from the REPL. Call the function and the prompt comes straight back; whatever flashed on screen is already gone.

So the job for this part is small to state: keep the program alive for as long as the window is open, and stop when it closes.

The event loop

A window that opens and closes again straight away isn't much of an app. To keep it on screen we need a loop: something that waits for the system to tell us what happened, and reacts.

We'll build that loop one piece at a time, starting from the smallest program that opens a window at all.

Here is the whole program so far. The function opens a window and then closes it. Run it and you'll see a flash, if you see anything.

Between opening and closing, we loop. Each pass asks the system for pending events and handles them, and we keep going until the window says it should close.

There's a problem. If anything inside the loop signals an error, we never reach the last line and the window is left hanging. Wrapping the loop in unwind-protect guarantees the cleanup runs. And while we're in there, each pass should draw a frame too.

That's a complete, well-behaved event loop in seven lines. All that's missing is something to draw.

Something to draw

The loop calls a function that doesn't exist yet. Its job is to paint one frame, and it will be called again on every pass, so it has to start from nothing each time.

Starting from nothing means clearing the window. This much already gives us a black rectangle that stays put, which is more than we had an hour ago.

Now something on top of it: a white square, forty points in from the corner.

A square that sits still doesn't prove the loop is running. Once we bind its position to the clock it slides across the window, one step per pass. Nothing appears, though, until we present the frame: everything before that was drawn off screen.

Run it again. The window stays open, the square moves, and closing the window ends the program. That is the whole skeleton of a native application.

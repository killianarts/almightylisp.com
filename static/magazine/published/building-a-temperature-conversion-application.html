01

Section 01 / 08

Now it's getting GUI

Now that we have a working system for making windows and starting an event loop, we want to add stuff to the window. We'll be building a temperature conversion application, so we'll need a place to type a number. To make it easy on ourselves, we'll only have one place to type the number, and then we'll have two buttons: one to convert from Fahrenheit to Celsius, and one for the reverse. They'll change the value of the number in the field where the original temperature was typed.

Understanding how to get a window open was challenging--we had to learn the inner workings of MacOS's GUI framework AppKit and how to use ClozureCL's Cocoa bridge to write Objective-C code in Common Lisp--but now that we understand the basics of working with AppKit, building the actual GUI isn't going to be that challenging.

Building the GUI is going to be fairly similar to building a CRUD application.

  1. We'll display a text input and buttons in a window.
  2. We'll code up a controller that has two actions: f-to-c and c-to-f.
  3. We'll write the code that models the "business logic" of converting temperatures.
  4. We'll wire up the model and controller code with the "views"--GUI widgets.

It'll end up feeling familiar to all my fellow web developers.

One important goal we have, however, is to write our code in a way that makes it hotswappable and interactive just like all Lisp code. We'll first muddle our way through the naive way before we upgrade to the more sophisticated approach. Future native application development will be made much easier after we learn the principles.

02

Section 02 / 08

A Refresher

First, let's just summarize what we covered in the last article:

  1. We learned how to interact with MacOS's GUI framework AppKit via ClozureCL's Cocoa bridge.
  2. We learned some of the details of Objective-C's syntax so we could understand how to write our Lisp code.
  3. We learned why we need an AppKit delegate to close our application and reopen the window in development.

Let's walk through the final code of that project piece by piece.

We begin by loading the Cocoa bridge.

We set up a delegate--an Objective-C object that AppKit asks whether it should quit the application when the window closes, and that we send a message to when we want the window reopened.

We split making a window and opening a window so that we can call make-window in the reopenWindow: method above without calling run again--which starts an event loop.

We wrote a function that sends a message on the main thread to the application's delegate that tells it to reopen the window.

And we wrote the entry-point for starting the application.

It was a lot to learn right from the beginning--selectors, delegates, main threads and event loops, an Objective-C and AppKit crash course, etc.

03

Section 03 / 08

Widgets

Thankfully, the next step in learning native programming isn't going to be quite as humbling. First, let's make the basic widgets, starting with a button.

Section 3.1

A Button

Making a button is easy thanks to ClozureCL's bridge--it has a convenient ns-button class that does the work of building the button in Objective-C. We just pass an ns-rect with the :with-frame argument. You can safely run this code without blowing up your REPL--you don't need to do it on the main thread.

We can make a small alias around ns:make-ns-rect to make future code easier to write.

Then we can rewrite the make-instance call.

The x and y coordinates refer to a position inside the view that the button will live in--for us, that will be the window's content view. If you're coming from the web, there's a trap here: the origin is the bottom-left corner, and y grows upward. A button at 0 0 sits in the bottom-left corner of the window, not the top-left.

Let's keep it in a variable so we can play with it.

A new button's title is an ns-string.

Which you can get back as a Lisp string using objc:lisp-string-from-nsstring.

...which isn't very helpful. We change it by sending the button the setTitle: message.

The #@ in front of the string is important. A Lisp string is not an Objective-C string, and AppKit only understands its own NSString objects. #@"F to C" is ClozureCL's reader macro for writing an NSString constant directly in your Lisp code.

Only ASCII in #@ strings

Keep the text in a #@ string to plain ASCII. I tried to use a nice arrow, as in #@"F → C", and the entire Lisp process died the moment the button was displayed. For anything fancier, or for a string that is only known at runtime, use (objc:make-nsstring "F → C"). As I wrote above, to go the other way, from an NSString to a Lisp string, use objc:lisp-string-from-nsstring.

Section 3.2

A Text Field

We also need somewhere to type the temperature. Unsurprisingly, AppKit's text input is called NSTextField, and it's made exactly the same way as the button.

Notice the y of 70. Since y grows upward, the text field is going to sit above the button we made at a y of 20.

Section 3.3

Putting Widgets in a Window

Making widgets in the REPL is safe, but we can't see them. A widget only appears on screen after it's added to a window. So let's start with the make-window function from last time, using our new rect function.

Every window comes with a contentView--the view that fills the window below the title bar. Think of it as the <body> of the window. Widgets are views too, and we add them to the content view with addSubview:.

Then we add the two buttons side by side under the text field.

If you still have the application running from last time, close the window, compile the new make-window, and call (reopen-window). Otherwise, compile the whole file and start the application with the process-interrupt line. You should see a small window with a text field and two buttons.

You can type in the field and you can click the buttons. Nothing happens when you click them, of course. We haven't told them what to do yet.

04

Section 04 / 08

Controller

In web programming, if we an interface to do something, we use a <form>.

When you click the button, it sends a message to the server (a request), which gets routed to the controller at do-this. The controller does something and replies to the message.

The same is true in AppKit. A button holds two things: a target and an action. The target is an object. The action is a selector--the name of a method. When you click the button, AppKit sends the action message to the target. This is called the target-action pattern, and it's used everywhere in AppKit.

So we need an object with two methods. This is our controller. Just like the delegate, it needs to be an Objective-C object so that AppKit can send it messages. It also needs to know about the text field, because that's where it will read the temperature from and write the converted temperature to.

Now we need the two actions. An action method always has the same shape: it takes one argument--the sender, which is the widget that was clicked--and returns nothing, which is :void in Objective-C. Since it takes an argument, the selector's name ends with a :. For now, the actions will just write something into the text field so that we know the buttons are working.

Objective-C's naming convention is camelCase, so our f-to-c and c-to-f actions become fToC: and cToF:. All that's left is the wiring.

In make-window, we make the controller and hand it the text field, then we set the target and action of each button.

You might wonder why the variable is named controller and not converter. It's because I tried converter first and ClozureCL refused to compile the function.

Class names are variables

When you define an Objective-C class with defclass, ClozureCL also makes a global variable with the same name that holds the class. That variable can't be rebound, so (let ((converter ...)) ...) fails with this error: CONVERTER is declared static and can not be bound. Give your local variables a different name than your Objective-C classes.

Close the window, compile, and call (reopen-window) again. Click the buttons and the text field tells you which button you clicked. The view is talking to the controller.

05

Section 05 / 08

Logic

Now for the "business logic". This is the easy part, and the best part: it has nothing to do with AppKit, Objective-C, or threads. It's just Lisp.

Because it's just Lisp, we can test it in the REPL without opening a window at all. Water boils at 212 degrees Fahrenheit.

And we can go back the other way.

Since we wrote the fractions as 5/9 and 9/5, Common Lisp does the math with rational numbers and we never lose any precision. That also means that a temperature that doesn't divide evenly comes back as a fraction.

That is the correct answer, but nobody wants to read 340/9 on a thermometer. We'll leave the logic precise and round the number only when we display it. format can do that for us.

Keeping the logic away from the GUI like this is the same separation we make in web applications, and for the same reasons. We can test it, reuse it, and when we later build the UI again with a different toolkit, this code won't change at all.

06

Section 06 / 08

Naive implementation

We have the views, the controller, and the logic. Now we connect them. When a button is clicked, we want to:

  1. Read the number in the text field.
  2. Convert it.
  3. Write the result back into the text field.

Both actions do the same thing with a different conversion, so we'll write one function that takes the conversion as an argument.

doubleValue asks the text field to read its text as a number and gives us a Lisp double float. If the text isn't a number at all--it's empty, or somebody typed "hot"--we get 0.0d0 instead of an error. Good enough for now. setStringValue: needs an NSString, and since our string is made at runtime by format, we convert it with objc:make-nsstring.

Then we rewrite the actions to call it.

Compile those three forms, but this time don't close the window. Type 212 into the text field that's already open and click "F to C". It says 100.0. Click "C to F" and it goes back to 212.0.

We redefined two Objective-C methods and the running application picked them up immediately. That's the Lisp experience we want. The same is true of convert-field and the conversion functions: redefine them and the very next click uses the new definition.

So the behavior of our application is already hotswappable. The trouble is everything else.

Section 6.1

The Trouble

Let's say we want to change the title of a button. We change the string in make-window, compile it, and... nothing. The window on the screen was built by the old make-window, and it has no idea that a new one exists. To see the change we have to close the window and call (reopen-window), and whatever we typed in the old window is gone.

That's the "edit, refresh the page" loop of web development. It's fine for three widgets. It won't be fine for a real application where getting back to the screen you were working on takes ten clicks.

What we really want is to reach into the running application from the REPL and change it. Let's imagine we had saved the window in a variable named *window* and tried to give it a title from the REPL.

No debugger, just a dead Lisp process and that message left behind in the *sly-inferior-lisp* buffer. It's the same lesson we learned last time when we tried to open a window: your REPL does not run on the main thread, and AppKit insists that its windows and views are only touched from the main thread. Some messages will kill the process like this one did, and some will just freeze your REPL. Either way, you're restarting Lisp.

We already know one way around this--it's how reopen-window works. We add a method to the delegate and use performSelectorOnMainThread: to send it the message. But that would mean writing a new Objective-C method for every single thing we ever want to do to the running application. That's not interactive development. That's filling out forms.

07

Section 07 / 08

Making it Hotswappable With a Main Thread Caller

What we want is to be able to write any Lisp code at all and say, "run this on the main thread".

The problem is that performSelectorOnMainThread: doesn't know what a Lisp function is. It only knows how to send a message to an Objective-C object. So we'll give it what it wants: an Objective-C object whose only job is to hold a Lisp function and to call it when it receives a message.

That's the only Objective-C method we'll need to write for this, ever. Now we write the Lisp function that uses it. It makes a caller that holds our function, asks AppKit to send the caller the callLispFunction: message on the main thread, and waits for it to finish.

The release at the end is new. Objective-C objects aren't garbage collected like Lisp objects are. Each one keeps a count of how many owners it has, and it's freed when the count reaches zero. We made the caller, so we own it, and when we're done with it we need to say so. Since we make a new caller for every call, we'd leak a little memory every time if we didn't.

This already works, but it throws away whatever our function returns. In a REPL we want to ask the running application questions, too. The function we pass and the function that calls it run on different threads, but a closure doesn't care about that. We can wrap our function in a lambda that saves the result in a variable, and return it after the main thread is done.

There's one more thing to take care of. If our function signals an error, it signals it on the main thread, in the middle of the application's event loop. I'm the one who made the mistake in the REPL, so I want the error in the REPL. We can do the same trick again: catch the error on the main thread, save it, and signal it again in the thread that asked.

Finally, since we're going to be typing this a lot, a small macro saves us from writing the lambda every time.

Section 7.1

Holding On To The Window

To poke at the window from the REPL, we need to be able to find it. We'll save it in a global variable when we make it.

There is one catch. By default, a window that isn't managed by a window controller is released when it's closed. Our variable would be left pointing at freed memory, and the next message we sent to it would crash the process. We tell the window not to do that with setReleasedWhenClosed:.

Reopening the window was the one thing we could already do on the main thread, and it took a delegate method and a function to do it. Now it's one line, and we can delete the reopenWindow: method from the delegate.

Compile the new definitions, close the old window, and call (reopen-window). We don't even need to restart Lisp to switch over to the new code. Now let's try setting the title again--the same code that killed our Lisp process before.

The title bar changes while the application is running, and the REPL is still alive. We can ask questions, too.

And if we make a mistake, we get an ordinary Lisp error in an ordinary Lisp debugger. Abort it and both the REPL and the application carry on as if nothing happened.

Section 7.2

Hotswapping the Widgets

We can now change anything in the running application from the REPL, but changing things by hand isn't the same as changing the code. We still have the original trouble: when we edit make-window, the open window doesn't change.

The reason is that make-window does two jobs. It makes a window, and it makes the content of the window. We split open-window last time for the same kind of reason, so let's split again. First, the buttons are getting repetitive, so they get a function of their own. It takes a Lisp string for the title, so we can finally have our arrows.

Then we move the widgets out of make-window and into a function that builds a fresh content view--an NSView, the plain rectangle that all widgets are built on--with everything already in it.

That leaves make-window with only the window to worry about. Instead of adding widgets to the content view the window came with, it replaces the whole content view with ours using setContentView:.

And here's the payoff. If a window's content view can be replaced when the window is made, it can be replaced at any time after that, too--as long as it's done on the main thread.

Compile the new definitions, close the window, and call (reopen-window) one last time. Now go to make-content, change the two titles to "F → C" and "C → F", compile the function, and evaluate this in the REPL.

The buttons change in the open window. Move a button, resize the text field, add a third button, compile, (refresh). The window never closes and the Lisp process never restarts.

If you've used a frontend framework, this will feel familiar: the content is whatever make-content returns, and we "re-render" by calling it again. It's crude--the text in the field is thrown away with the old content view, for example--but it's the whole principle of hotswapping a native GUI in a few lines of code:

  1. Keep a reference to the things you want to change.
  2. Build them in functions you can call again.
  3. Have one way to run any code on the main thread.

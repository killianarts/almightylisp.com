What do you mean by "native" application?

When first setting out to make this native application for my father, I thought it would good to first learn how to open a window in MacOS from Common Lisp since I'd never done it before. But straight from the beginning, I was faced with answering the question: What kind of native application?

In the beginning, I am fine with creating something that is only usable on MacOS--LLMs these days seem quite capable of translating from one environment to another anyhow. But ultimately, I want to make a cross-platform application usable on Windows, MacOS, and even Linux. To achieve that, what will my final architecture(s) look like?

You see, there isn't just one way to build a native GUI application. There are actually roughly three architectures to choose from:

  1. Ported native: Use the operating system's API to build the UI--porting the UI to other operating systems.
  2. Cross-platform native: Use a framework like KDE, GTK, etc. to build the UI.
  3. Custom native: Use a custom UI framework that you port to the platforms you wish to support.

The choice is especially important when you want to build a cross-platform application because of the strengths and weaknesses of each approach.

Strengths:

  • Looks and feels familiar; fits in with the OS's other applications.
  • Likely popular with lots of help online.
  • Lots of examples to learn from.
  • Known to work.
  • Well supported.

However, there are some important weaknesses especially when you want to build something cross-platform:

  • Probably has an old API with lots of backwards compatibility-related cruft you need to deal with.
  • You have to build the UI once per platform you want to build for; maintainence means keeping all those UIs in-sync.

The "true" path is a complicated and time/token intensive venture.

And in reality, some of the pros might be overstated. MS Office applications look nothing like Notepad or the Start Menu; MacOS infamously has multiple border radiuses and the "style" is routinely "updated" ala liquid glass which you don't just get automatically in your application and may not even like; building directly in Objective-C or C++ is much more well-supported than building in Common Lisp; Look and feel in Linux isn't standardized--you application will only look and feel familiar on a per GUI framework basis.

But again, the weaknesses are also a bit overblown. While you may initially need to write for several platforms, you can create a framework wrapping the platform APIs so that you can still code once and run anywhere. That is, in fact what LispWorks does with their CAPI GUI toolkit.

So although intuitively the ported path would seem like the path to a "pure" native application, the reality is far dirtier.

The cross-platform approach means using something like KDE, GTK, etc. to make the GUI. Since those toolkits work on multiple platforms, you get cross-platform support for free. The main strength of this approad is that you build once, then your application works on multiple platforms; no need for OS-specific code.

The weaknesses are that it will feel alien, and potentially cheap/retro. Typically you would also be limited by what Common Lisp libraries exist for those toolkits. If the GTK ones are more mature, but you like KDE more, then you have a conundrum.

In this approach, you need to actually do the work of drawing the pixels on the screen. Instead of using an OS API or cross-platform toolkit, you make your own toolkit, creating the API for building interfaces the way you like. This approach has some significant strengths and weaknesses.

Strengths:

  • You don't have to learn how other people draw pixels, work with text, style, etc. You decide the way UIs are built.
  • Your application won't be a Windows or MacOS application, nor will it be a GTK application--it will be your application.

The strengths mean maximum ownership and control. Of course, you can imagine the weaknesses:

  • You don't get to benefit from the work of others at all--you are on your own.
  • Lots of work, requires a knowledge of doing pixel-drawing.
  • Won't fit in anywhere. Completely unique, but alien.

This is the approach used in some rather complex software like Photoshop, JetBrains IDEs, etc.

Notably, the Zen code editor uses this approach with their own custom toolkit called GPUI. This toolkit has an API that will look familiar to front-end developers. From their homepage:

This has a distinctly Tailwind flavor to it.

Given that we have a large surplus population of front-end and fullstack developers who I believe will be redirected towards building native UIs, there is a strong possibility that this approach will be the ascendant one for the next decade. The largest variable is whether said developers will even be looking at the code, in which case web-like API will mean less to them than other factors (speed and efficiency).

Starting Small, Thinking Big

So the question is: for my first application, where do I begin?

The correct approach I believe is to start with the easiest thing possible, learn the native paradigm, and then adapt as I learn and gain experience. That means for now I will be making a native MacOS application.

For native MacOS development, there are two options:

  1. Build with Clozure CL. It includes a special API for working with Objective-C in Common Lisp.
  2. Build with cl-nextstep. Less mature, but allows me to write cross-implementation compatible code instead of code specific for Clozure.

Because LLMs are so good at converting code from one framework/language to another, and because I don't plan on making this the final architecture choice for this application, the choice isn't very important. For fun, I am going to use Clozure.

However, given the capabilities of the latest LLMs, in the future I will try making a custom GUI framework. Whether I go with a web-like API or something else is something to decide later.

Now that the NSApp variable is set to the application object, we begin configuring the application.

Applications in MacOS can either be a background process, in which case you don't want a Dock icon or menu bar, or they can be menu bar icon applications, or they can be a full-blown application that can come into the foreground. We want the last one--a regular application.

Here we make the window object. Windows in AppKit have what is called a content rect, the rectangle or box that holds everything in it. A rect has four values: x coordinant, y coordinant, width, and height.

A style mask is a configuration setting for how the window should look and act--should it have borders, should it have a title bar, should it be resizable, etc.

The logior setting here might not be familiar to you if you're a simple web dev like me. Bits have an on and off state--1 or 0. There are different ways to modify a certain set of bits--called bitwise operations--and logior is one of them.

Each style mask is set to a numeric value. logior combines those values at the bit level. The above style masks (Titled and Closable) have values 1 and 2. At the bit level, they are represented as follows:

logior forms the union of the two, 0011.

In any case, the exact settings for the style mask are stored as a combined set of bits.

The backing is related to how the window should use pixels written elsewhere in memory. For modern applications, it should always be set to NSBackingStoreBuffered.

defer refers to whether a window's resources should be allocated immediately or if the resources should be allocated after it is opened. For windows you are about to display, :defer nil is what you want.

One application can have multiple windows displayed at once (think Photoshop). makeKeyAndOrderFront sets whether a window should be the one "on top of" or in front of the others.

And of course, you can have multiple applications open. activateIgnoringOtherApps is used to either have the application open in front of or behind the others.

run does what you imagine, but what you might not know is that applications have what is called an event loop which waits for events. Events queue up and are processed in order by the loop.

In MacOS, the event loop for an application needs to be started on the main thread. This will become relevant shortly.

Simply called (open-window) won't work--it will immediately blow up your REPL without signaling an error. When that happens--no debugger, just a dead Lisp process--that means there was an error on the Objective-C side.

The reason for the error is that MacOS apps need to open on the main thread. In the Objective-C code, we don't see any reference to the main thread because it will naturally do it; there's no need to explicitly reference the main thread.

That is not the case with Common Lisp. We need to purposefully set the open-window function as the process on the main thread. process-interrupt will tell *initial-process*--the main thread--to stop what it's doing and run the open-window function.

Making it close properly

When you close the window, you'll notice that the icon in the Dock sticks around. That's because the window is closed, but the process is still running.

To get it to close the process properly as we expect, we need to assign a delegate object to the application object.

Why do we need this "delegate" thing? When you close the window, AppKit gets the close event and asks, "Should I terminate the process?" But AppKit asks the delegate. If the delegate doesn't exist, then AppKit defaults to not terminating the process.

app-delegate looks like a regular Lisp class definition, but the :metaclass ns:+ns-object part of the definition makes this an Objective-C class. The same is true of the objc:defmethod--it's an Objective-C method for the appDelegate class (in Objective-C).

The protocol for Objective-C methods for AppKit objects includes a method called applicationShouldTerminateAfterLastWindowClosed: (mind the :) that returns a boolean value. If the application object has a delegate, when the AppKit goes to ask the delegate, "Should I terminate the process?", the answer the delegate returns is the return value of applicationShouldTerminateAfterLastWindowClosed:.

Reopening A Window

Now we have a problem: If we set :quit-on-close to nil, we can't reopen the window. Click on the icon in the Dock... nothing. Rerun (ccl:process-interrupt ccl::*initial-process* #'open-window)... nothing. process-interrupt won't interrupt the first open-window event loop.
